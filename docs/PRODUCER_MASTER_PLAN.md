## 0. この文書の役割

既存文書は、ゲームルール、状態遷移、技術、得点、操作を詳しく定めている。一方で、制作を最後まで運ぶために必要な次の判断が不足していた。

- 誰に、どのような価値を届けるゲームなのか。
- 現在の「最小版」が、試作、縦切り完成版、製品版のどれなのか。
- 何を必ず作り、何を後回しにし、何を作らないのか。
- 面白くない状態のまま作業を続けないため、どこで止めるのか。
- どの証拠がそろえば次の制作段階へ進めるのか。
- 1.0公開時に、どの規模と品質を目指すのか。
- プレイテストの結果を、どの基準で採用、修正、中止へつなげるのか。
- PRごとに、誰が何を確認し、何を報告するのか。

本書は、これらの制作判断を正式化する。

### 0.1 文書ごとの決定権

文書を単純な一列の上下関係だけで扱わず、分野ごとに決定権を分ける。

| 分野 | 正式な参照先 |
|---|---|
| 実装上の禁止事項、入力、時間、得点、衝突の契約 | `IMPLEMENTATION_CONTRACT.md` |
| 制作範囲、優先順位、節目、公開判断 | `PRODUCER_MASTER_PLAN.md`（本書） |
| 動物、危険種、群れ、囲いの状態 | `STATE_TRANSITION_SPEC.md` |
| 面白さ、操作感、演出、得点意図 | `GAME_DESIGN_MASTER_PLAN.md` |
| 技術選定、構成、性能、基本実装順 | `IMPLEMENTATION_PLAN.md` |

同じ分野で記述が食い違った場合は、上表の正式な参照先を優先する。本書は、実装契約や状態遷移の細部を勝手に上書きしない。

## 1. プロデューサー検証の結論

### 1.1 現在の強み

OITATEには、製品として育てる価値がある中心があります。

- 動物を直接操作せず、主人公の位置と合図で間接的に動かす。
- 同じ入力でも、動物の種類と状況で反応が変わる。
- 危険種、地形、囲いによって、行動の順序を考える必要がある。
- ミスを予告し、救助と立て直しを遊びに含める。
- 速さだけではなく、安全、統率、危険管理を評価する。

この中心は、一般的な追い込みゲーム、単純な道順パズル、直接命令型の戦略ゲームと区別できます。

### 1.2 現在の弱み

実装仕様は詳しいものの、制作計画としては次の危険が残っていました。

1. 現在の「最小版」が、実際には多くの完成要素を含む縦切り完成版である。
2. 最初の面白さが確認できる前に、得点、設定、音、救助、3種類11体を作る危険がある。
3. 1.0の規模が決まらず、6種類、6ステージ、追加環境が無制限に膨らむ可能性がある。
4. 制作PRが技術単位で定義され、製品として次へ進める証拠が弱い。
5. 初見理解、再挑戦、得点改善を測る数値はあるが、合否判定が不足している。
6. 公開ページ、説明文、画像、対応端末、アクセシビリティ説明など、公開物の準備が計画外だった。
7. 新しい案を追加する際の承認と削減ルールがない。

本書では、機能を増やすのではなく、制作の順序、削る基準、公開条件を追加する。

### 1.3 実装開始の判定

**実装は開始可能だが、最初から現在の縦切り完成版を一括で作らないことを条件とする。**

先に、主人公1人と臆病種1〜3体で「位置取りによって意図した方向へ動かせること」が面白いかを確認する。この確認に失敗した場合、得点、危険種、完成素材へ進まない。

## 2. 製品の定義

### 2.1 一文で説明する

> 動物を直接命令せず、自分の立ち位置と二つの合図を使い、性質の異なる群れを安全な囲いへ導く3Dアクションパズル。

公開時の短い訴求は、次を候補とする。

> 動かすのは動物ではなく、あなたの立ち位置。

### 2.2 プレイヤーへ約束すること

OITATEは、次の5点を製品の約束とする。

1. **反応を読める**
   - 動物の行動には理由があり、姿勢、向き、音、記号から予測できる。
2. **考え方と操作の両方で上達できる**
   - 正しい順序だけでも、反射神経だけでも最高評価にならない。
3. **失敗から学べる**
   - 画面外やランダムな失敗ではなく、原因と改善方法を示す。
4. **一つの正解へ縛られない**
   - 安全な遠回りと、精度が必要な近道を成立させる。
5. **短い一面でも達成感がある**
   - 観察、計画、危機、立て直し、収容、評価までを一つの流れで体験できる。

### 2.3 主な対象プレイヤー

年齢だけでなく、好む遊び方で定義する。

**主な対象**

- ルールを観察し、試行錯誤して解くアクションパズルが好きな人。
- 直接攻撃より、位置取りや誘導で状況を変えるゲームが好きな人。
- 1回4〜8分程度のステージを、得点改善のために繰り返せる人。
- スマートフォンでも、移動とカメラを使う3Dゲームを遊べる人。

**次に狙う対象**

- 安全評価や最短時間を詰めるスコア挑戦が好きな人。
- 動物の反応や低ポリゴンの世界観を楽しみたい人。
- PCやiPadで、少し落ち着いてパズルを遊びたい人。

### 2.4 主な対象にしない遊び

次の期待を持つ人へ、別のゲームだと誤認させない。

- 動物を育成する農場運営ゲーム。
- 広い世界を自由に探索するオープンワールド。
- 危険種を倒す戦闘ゲーム。
- 一つの指だけで即座に遊べる超短時間ゲーム。
- 大量の動物が物理演算で混乱する観賞用シミュレーター。

### 2.5 製品の4本柱

| 柱 | 内容 | 失った場合の問題 |
|---|---|---|
| 読める動物反応 | 次の行動を予備動作で伝える | 間接操作が理不尽になる |
| 位置取りによる誘導 | 主人公の立つ場所と速度が結果を変える | 合図ボタンを押すだけになる |
| 種類同士の関係 | 動物、危険、地形、囲いの相性が順序を作る | 単純な運搬作業になる |
| 改善できる評価 | 結果から次の試行を変えられる | 1回クリアして終わる |

### 2.6 作らない方向

品質を守るため、次を反対の設計方針として明記する。

- 種類数を増やすだけで深さを出さない。
- 動物の速度を上げるだけで難しくしない。
- 物理演算の偶然を攻略の中心にしない。
- 長い説明文でルールを理解させない。
- 時間だけを最高評価の中心にしない。
- 初回から大量の設定選択を要求しない。
- 元作品の名称、外見、画面、ステージを再現しない。

## 3. 制作段階の用語を整理する

これまで「最小版」と呼んでいた内容は、一般的な最小試作ではなく、完成品質を一面へ集約した**縦切り完成版（Vertical Slice）**である。

今後は次の用語へ統一する。

| 段階 | 目的 | 含むもの |
|---|---|---|
| 操作試作 | 移動とカメラが成立するか | 主人公、平地、仮動物1体 |
| 面白さ試作 | 接近誘導だけで面白さがあるか | 臆病種3体、囲い1つ |
| 最初に遊べる版 | 群れを安定して収容できるか | 臆病種6体、基本UI、再開 |
| 危険検証版 | 危険種の誘導と救助が成立するか | 危険種、専用囲い、救助 |
| 縦切り完成版 | 製品の代表的な一面を完成品質で示す | 3種類11体、得点、説明、仮完成演出 |
| 1.0製品版 | 公開作品として十分な内容を持つ | 練習、6ステージ、4種類まで |

### 3.1 重要な変更

- 現在の計画にある「1ステージ、3種類、11体、得点、設定、音」は、**縦切り完成版の範囲**とする。
- 面白さ試作の段階では、危険種、救助、得点、完成素材を作らない。
- 縦切り完成版が合格する前に、2面目以降を作らない。
- 1.0で追加する動物は、合計4種類までを基本上限とする。
- 5種類目と6種類目は、1.0公開後の候補へ移す。

## 4. 1.0製品版の範囲

### 4.1 1.0で必ず含める

- 操作を安全に試せる短い練習または段階的な初回説明。
- 完成した6ステージ。
- 3種類の縦切り動物。
- 条件を満たした場合だけ追加する第4の動物。
- 接近圧力、誘導音、威嚇音の3手段。
- 水、狭路、危険区域など、最低3種類の地形判断。
- 安全、統率、危険管理、時間の評価。
- 標準、補助あり、練習の記録分離。
- 端末内の進行、最高評価、最高得点保存。
- iPhone横画面を主基準にした操作。
- iPad、PCの補助操作。
- 音なし、振動なしでも遊べる表示。
- 公開ページ、操作説明、対応端末、権利表示。

### 4.2 第4の動物を追加する条件

第4の動物は、見た目や速度だけが違う場合は追加しない。次のうち最低2項目を変える必要がある。

- 主人公の合図への反応。
- 群れとの関係。
- 危険種との関係。
- 通れる地形。
- 囲いへ入る条件。
- ほかの動物を利用する順序。

さらに、新しい操作ボタンを増やさず、既存の3手段で誘導できなければならない。

### 4.3 1.0で含めない

- 5種類目、6種類目の動物。
- オンラインランキング。
- 日替わりステージ。
- ランダム生成。
- アカウント。
- 課金。
- 装備、成長、収集物。
- 長い物語と会話イベント。
- 本格的なステージエディター。
- 押せる箱、落下物、複雑な剛体物理。
- 広い探索マップ。
- プレイヤー同士の通信。

### 4.4 目標とする遊ぶ長さ

| 単位 | 目標 |
|---|---:|
| 通常ステージの初回 | 5〜10分 |
| 一度理解したステージ | 4〜7分 |
| 高評価を狙う再挑戦 | 3〜6分 |
| 1.0の初回完了 | 30〜50分程度を目安 |

これらは強制的な制限時間ではない。公開前のプレイテストで実際の分布を確認し、極端に長い停滞があればステージを修正する。

## 5. プレイヤー体験の流れ

### 5.1 起動から最初の成功まで

ブラウザゲームは、プレイ前の離脱を防ぐ必要がある。起動後は次を目標にする。

| 出来事 | 目標 |
|---|---:|
| 最初の表示または読み込み表示 | 1秒以内 |
| 操作可能 | 15秒以内 |
| プレイヤーの最初の移動 | 操作可能から15秒以内 |
| 動物が意図に反応する最初の経験 | 45秒以内 |
| 最初の小さな収容成功 | 90秒以内 |

最初に設定一覧を表示しない。標準設定で開始でき、必要な設定は開始画面または一時停止画面から変更できるようにする。

### 5.2 一面の感情の流れ

各ステージは、次の流れを持たせる。

1. **観察**
   - 動物、囲い、危険、経路を確認する。
2. **小さな成功**
   - 比較的安全な動物を短く動かし、操作への信頼を作る。
3. **組み合わせの発見**
   - 合図の副作用や地形差に気づく。
4. **危機**
   - 危険種、群れ分裂、経路競合のいずれかが起きる。
5. **立て直し**
   - 救助、距離を取る、待機場所を使う。
6. **最後の収容**
   - 最も大きな群れまたは危険種を確定する。
7. **振り返り**
   - 評価と改善点を確認する。

高い緊張が続くだけの面にしない。危険の前後に、状況を読み直せる短い余白を設ける。

### 5.3 一面で教える内容の上限

1ステージで新しく教える中心概念は1つ、補助概念は1つまでとする。

例：

- 中心概念：浅い水を通れる動物と避ける動物。
- 補助概念：追従種は主人公が速すぎると列から離れる。

新しい動物、新しい地形、新しい囲い、新しい危険を同時に初登場させない。

### 5.4 縦切り完成版の初回説明

縦切り完成版では、全機能を検証するため、短い安全区画で3種類を順に試してよい。ただし、これは1.0の最終的な導入方法ではない。

1.0では、次のように分散して教える。

- ステージ1：接近圧力。
- ステージ2：誘導音と水。
- ステージ3：危険種と威嚇音。
- ステージ4以降：副作用と複数種類の同時管理。

初回説明は、短く、操作型で、スキップ可能にする。経過時間ではなく達成条件で進める。

## 6. 結果画面の製品判断

100,000点の内部計算は維持するが、初見プレイヤーへ最初に大きな数字だけを見せない。

### 6.1 表示順

1. S〜Cの総合評価。
2. そのプレイの強みを示す称号または一文。
3. 安全、統率、危険管理、時間の4本の評価。
4. 次回に改善する内容を一つ。
5. 再挑戦ボタン。
6. 詳細を開いた場合だけ、100,000点の内訳と出来事記録。

### 6.2 理由

- 大きな合計点だけでは、何を直すべきか分からない。
- 4項目を同時に細かく説明すると、結果画面が読みづらい。
- 最初は「よかった点」と「次に一つ直す点」へ絞る。
- 詳細な数値は、得点を詰めたいプレイヤーだけが確認できればよい。

### 6.3 再挑戦を促す条件

結果画面では、次のどれか一つだけを示す。

- 前回より上がった項目。
- あと少しで上の評価に届く項目。
- 最も大きく失った項目。
- 新しく獲得できそうな称号。

不安をあおる連続通知、報酬受け取り、広告、課金は入れない。

## 7. 縦切り完成版の機能優先順位

### 7.1 必須（Must）

縦切り完成版の公開判断に必須とする。

- 主人公の移動、歩行、走行。
- iPhone向けカメラと入力の安定。
- 臆病種、追従種、危険種の3種類。
- 接近圧力、誘導音、威嚇音。
- 群れ、緊張、混乱、危険予告、救助。
- 通常動物と危険種の収容。
- 1つの完成ステージ。
- 安全な手順と速い手順の最低2経路。
- S〜C評価と4項目の得点。
- 即時再挑戦。
- 基本的な説明、目的、残数、警告。
- 音なしでも成立する視覚表示。
- 色だけへ依存しない種類と囲いの識別。
- 診断情報、再現情報、テスト。
- 目標端末での性能と安定。
- 素材とOSSの権利確認。

### 7.2 公開前に強く望む（Should）

品質へ大きく影響するが、面白さ試作では後回しにできる。

- 種類別の効果音と危険警告音。
- 左利き用の操作配置。
- ボタンと仮想スティックの大きさ設定。
- 補助ありモード。
- 端末内の最高記録。
- 低負荷と標準の画質設定。
- 完成した低ポリゴンモデルと主要アニメーション。
- 失敗原因に応じた結果画面の助言。

### 7.3 余裕がある場合（Could）

縦切り完成版の公開を遅らせてまで入れない。

- 振動パターン。
- ゲームパッド。
- 詳細な統計画面。
- リプレイ経路表示。
- 高度なカメラ設定。
- 複数の環境音。
- 追加称号。

### 7.4 縦切り完成版では作らない（Won't）

- 2面目以降。
- 第4の動物。
- オンライン機能。
- ランダム生成。
- 本格的な物語。
- ステージエディター。
- 収益化。

## 8. 制作の節目と進行判定

各節目では、**進行、修正、削減、中止**の4判断を行う。PRが技術的に成功しただけでは進行しない。

### P0：製品方針の固定

**確認すること**

- 一文説明、対象プレイヤー、4本柱、作らない方向が承認されている。
- 縦切り完成版と1.0の範囲が分かれている。
- 5種類目、6種類目を1.0へ入れない方針が理解されている。

**進行条件**

- 本書がマージされる。
- ユーザーが実装開始を明示する。

### P1：操作試作

**内容**

- 主人公1人。
- 平地。
- 仮動物1体。
- 左移動、右カメラ、歩行と走行。

**証拠**

- iPhone実機の操作確認。
- 入力取りこぼし、カメラ操作時間、画面回転復帰の記録。
- 目標端末の画面更新速度。

**進行条件**

- 移動、カメラ、合図を同時に使っても入力が失われない。
- 自動カメラで主人公の進行方向が勝手に変わらない。
- 初見3〜5人の過半数が、30秒以内に移動とカメラを扱える。

**不合格時**

- 動物数を増やさない。
- カメラ、入力領域、移動基準を修正する。

### P2：面白さ試作

**内容**

- 臆病種3体。
- 囲い1つ。
- 接近圧力のみ。
- 得点、危険種、完成素材なし。

**証拠**

- 初見5人前後のプレイ。
- 90秒以内に意図した方向へ動かせた人数。
- 操作後に「なぜ動いたか」を説明できた人数。
- 自発的な再挑戦の有無。

**進行条件**

- 初見の70%以上が、90秒以内に少なくとも1回、意図した方向へ群れを動かせる。
- 80%以上が、主人公の位置と動物の移動方向の関係を説明できる。
- 過半数が、指示されずにもう一度試す、または操作改善を試みる。

**不合格時**

- 緊張、個体差、危険種を追加しない。
- 圧力範囲、予備動作、カメラ、囲い前の空間を修正する。
- 2回の大きな修正後も成立しない場合は、3D視点または中心ルールを再検討する。

### P3：最初に遊べる版

**内容**

- 臆病種6体。
- 群れ、緊張、混乱。
- 囲い入口予約と詰まり復帰。
- 即時再挑戦。

**進行条件**

- 正しい位置取りで、5回中5回クリアできる再現性がある。
- 技術的な詰まりによる失敗が20回中1回以下。
- 混乱した主原因を、プレイ後に説明できる。
- 歩行と走行の使い分けがプレイ結果へ表れる。

**不合格時**

- 追従種と危険種を追加しない。
- 緊張の要因を減らすか、群れ処理を単純化する。

### P4：危険検証版

**内容**

- 危険種単体の索敵、追跡、狙い、飛びかかり。
- 威嚇音。
- 危険種専用囲い。
- 救助。

**進行条件**

- 危険種の狙いを初見の80%以上が攻撃前に認識できる。
- 危険種を囲いへ入れる条件を、長文説明なしで理解できる。
- 危険種単体を5回連続で収容できる。
- 救助成功と失敗の理由を説明できる。

**不合格時**

- 11体の統合へ進まない。
- 救助が複雑すぎる場合は、救助時間、威嚇耐性、攻撃段階を減らす。

### P5：縦切り統合版

**内容**

- 3種類11体。
- 地形差。
- 安全な経路と速い経路。
- 仮の結果画面。

**進行条件**

- 初見の60〜80%が12分以内にクリアできる。
- 80%以上が、3種類の違いを一つ以上説明できる。
- 80%以上が、失敗時に次へ変える行動を一つ説明できる。
- テスターが、安全な経路と速い経路の両方を実際に発見または利用できる。
- カメラや入力が原因の失敗が全試行の10%未満。

**不合格時**

- 得点の細部、完成素材、2面目へ進まない。
- 同時に見る要素、地形、動物数を減らす。

### P6：縦切り完成版

**内容**

- 完成した1ステージ。
- 初回説明。
- 得点、称号、助言、記録。
- 主要な仮完成モデル、音、設定。
- 公開ページの仮版。

**進行条件**

- 初見8〜12人で、P5の基準を再度満たす。
- クリア者の50%以上が、指示なしで再挑戦する。
- 再挑戦者の70%以上が、得点、評価項目、または時間のいずれかを改善する。
- 結果画面の助言と、実際の改善方法が一致する。
- 標準と補助ありの記録が混ざらない。
- 目標端末の性能、読み込み、安定条件を満たす。

**進行後**

- 初めて2面目以降の制作を許可する。
- 第4の動物は別の小試作で検証する。

### P7：1.0内容完成

**内容**

- 練習または段階的説明。
- 6ステージ。
- 合格した場合のみ第4の動物。
- 進行保存。
- 全ステージの得点と評価。

**進行条件**

- 各ステージが新しい中心概念を一つ持つ。
- 同じステージの配置替えだけになっていない。
- 最初から最後まで進行不能がない。
- 主要な制作物とライセンスが確定している。
- 全体を初見で遊ぶテストを実施している。

### P8：公開候補版

**内容**

- 不具合修正。
- 容量、性能、対応端末の確定。
- 公開ページ、画像、動画、操作説明、権利表示。
- 既知問題とサポート範囲。

**公開条件**

- 後述の公開品質条件をすべて満たす。
- 致命的、進行不能、記録破損の既知問題がない。
- ユーザーが公開を明示承認する。

## 9. プレイテストで測る指標

外部の一般的な平均値を、そのまま合否へ使わない。OITATE自身の試験結果を制作判断へ使う。

### 9.1 中心指標

| 指標 | 定義 | 縦切り完成版の目標 |
|---|---|---:|
| 操作可能まで | ページを開いてから操作できるまで | 15秒以内 |
| 最初の意味ある入力 | 操作可能から主人公を動かすまで | 15秒以内 |
| 最初の反応理解 | 意図した方向へ動物を動かすまで | 45〜90秒以内 |
| 最初の収容 | 最初の小さな成功まで | 90秒以内を目標 |
| 初回クリア率 | 初見で12分以内にクリア | 60〜80% |
| 失敗理解率 | 次に変える行動を説明できる | 80%以上 |
| 種類理解率 | 3種類の違いを説明できる | 80%以上 |
| 自発的再挑戦率 | 指示なしで再度開始 | 50%以上 |
| 二回目改善率 | 得点、評価項目、時間のどれかが改善 | 70%以上 |
| 技術的失敗率 | 入力、カメラ、詰まり、復帰の問題で失敗 | 10%未満 |
| 手動カメラ負担 | 通常プレイ時間に占める手動カメラ操作 | 25%未満を目安 |

### 9.2 指標の扱い

- 少人数の結果を統計的な事実として断定しない。
- 数値と、プレイヤーが口にした理由の両方を見る。
- 1人の熟練者の高評価だけで難易度を決めない。
- 全員が失敗した場所を「難しいからよい」と扱わない。
- 入力やカメラの問題を、プレイヤーの技量不足にしない。

### 9.3 公開後に見る指標

サーバー解析は1.0の必須ではない。公開版で外部送信を行う場合は、目的、保存期間、同意、プライバシー説明を別途承認する。

まずは次を端末内または任意の診断共有で確認する。

- 起動から開始まで。
- 開始から最初の収容まで。
- ステージごとのクリアと中断。
- 再挑戦。
- 失敗原因。
- 得点分布。
- 補助設定の利用。
- カメラ操作時間。
- 技術的な自動復帰回数。

---

## 10. プレイテストの実施段階

| 段階 | 初見人数の目安 | 主な目的 |
|---|---:|---|
| P1 | 3〜5人 | 移動、カメラ、誤操作 |
| P2 | 5人前後 | 接近誘導の理解と面白さ |
| P4 | 5〜8人 | 危険予告、収容、救助 |
| P5 | 5〜8人 | 3種類統合と複数解 |
| P6 | 8〜12人 | 初回クリア、再挑戦、得点理解 |
| P8 | 複数端末と複数プレイヤー | 公開品質、性能、全体進行 |

### 10.1 テスト中に聞く質問

プレイ中は操作方法を教えすぎない。終了後に次を確認する。

1. このゲームの目的を一文で説明してください。
2. 3種類の動物は何が違いましたか。
3. 一番困った場面はどこでしたか。
4. その原因は、自分の判断、操作、画面、動物の動きのどれだと思いますか。
5. もう一度遊ぶ場合、何を変えますか。
6. 結果画面のどこを最初に見ましたか。
7. 得点を上げる方法が分かりましたか。
8. 画面外の危険や目的地を見失いましたか。

### 10.2 診断データ

開発版では、プレイ終了後に診断JSONを共有できるようにする。

- コミット番号。
- ステージ版。
- 端末と画面サイズ。
- 設定と補助。
- 乱数の種。
- 入力履歴。
- 状態遷移。
- 失敗またはクリア原因。
- 得点イベント。
- 性能と自動復帰。

個人名、連絡先、端末固有識別子を含めない。

## 11. 範囲変更の規則

### 11.1 新要素を追加する条件

縦切り完成版の範囲固定後、新機能を追加する場合は、同等以上の作業を一つ削るか、1.0後へ移す。これを**一つ追加するなら一つ外す規則**とする。

### 11.2 明示承認が必要な変更

次は、ユーザーの承認なしに変更しない。

- 製品の4本柱。
- 主な対象プレイヤー。
- 3種類の中心動物。
- 操作ボタンの追加。
- 得点の4項目と比率。
- 標準、補助あり、練習の区分。
- 縦切り完成版と1.0の範囲。
- 対応端末の主基準。
- オンライン、課金、広告、アカウントの追加。
- 元作品との距離を縮める名称、外見、ステージ案。

### 11.3 証拠があれば担当判断で調整できる変更

次は、承認済みの範囲内で、プレイテストと実機結果を示せば調整できる。

- 動物の速度、距離、時間。
- 緊張の増減量。
- カメラ速度と注視比率。
- 囲い入口の幅。
- 得点の細かな減点値。
- 目標時間。
- 仮想スティックの感度。
- 警告表示の時間。

ただし、変更前後の数値、理由、結果をPRへ記録する。

### 11.4 機能要望の扱い

1人の意見だけで追加を決めない。次の順で判断する。

1. 製品の4本柱へ関係するか。
2. 複数人が同じ問題を経験したか。
3. 既存機能の修正で解決できないか。
4. 新機能を入れる場合、何を外すか。
5. 縦切り完成版または1.0の公開を遅らせる価値があるか。

## 12. PRに必要なプロデューサー情報

すべての実装PRは、技術差分だけでなく、プレイヤーへの影響を説明する。

### 12.1 PR本文の必須項目

- このPRが証明する遊び。
- プレイヤーから見て何が変わるか。
- 今回は何を作らないか。
- 関係する制作段階と進行条件。
- 自動試験の結果。
- 実機確認の結果。
- プレイテストの人数と結果。対象外なら理由。
- 性能、容量、入力への影響。
- 既知問題。
- 次工程へ進めるか、修正が必要か。
- 戻す場合の方法。

### 12.2 PRの判定

| 判定 | 意味 |
|---|---|
| 進行 | 次の制作段階へ進める証拠がある |
| 修正 | 方針は維持し、このPR内または後続で直す |
| 削減 | 複雑さを下げ、要素を減らす |
| 中止 | 中心が成立せず、次工程へ進まない |

### 12.3 1つのPRへ入れすぎない

6つの大きな実装PRという全体方針は維持する。ただし、PR内の中止判定を通る前に、後半の機能を実装しない。

例としてPR 3では、臆病種3体の基本誘導が不合格なら、6体、緊張、混乱、入口予約へ進まない。

## 13. 役割と最終判断

同じAIまたは同じ作業者が複数役を担当してもよい。ただし、PRではどの観点で確認したかを分けて記録する。

| 役割 | 主な責任 | 最終判断 |
|---|---|---|
| 製品責任者 | 作品の目的、範囲、公開 | ユーザー |
| ゲームプロデューサー | 範囲、節目、リスク、進行判定 | ユーザー承認案を作る |
| ゲームデザイナー | ルール、数値、ステージ、得点 | 正式仕様内で提案 |
| 技術責任者 | 構成、性能、依存、保守 | 技術合否を報告 |
| 操作・画面担当 | 入力、カメラ、説明、アクセシビリティ | プレイ試験で合否を報告 |
| アート・音担当 | 輪郭、動作、音、容量、権利 | 制作基準への適合を報告 |
| 品質担当 | 自動試験、実機、敵対的検証 | 公開を妨げる問題を報告 |
| 公開担当 | Pages、説明、画像、ライセンス、既知問題 | 公開候補を作る |

### 13.1 ユーザーの明示承認が必要な操作

- PRをReadyにする。
- PRをマージする。
- 次の制作段階へ進む。
- 公開範囲を広げる。
- 1.0の範囲を変える。
- オンライン機能、広告、課金を追加する。

## 14. ステージ制作の型

各ステージは、次の項目を定義してから作る。

| 項目 | 内容 |
|---|---|
| 中心概念 | この面で新しく理解する一つのこと |
| 補助概念 | 中心を補う一つのこと |
| 初期配置 | 動物、危険、囲い、待機場所 |
| 安全な経路 | 初見でも発見しやすい遠回り |
| 熟練経路 | 高精度だが安全と速度を両立できる近道 |
| 回復手段 | ミス後に詰まず戻せる方法 |
| 最大同時情報 | 同時に管理する群れと危険の数 |
| 目標時間 | 初回、理解後、高評価の目安 |
| 得点の中心 | この面で主に改善する評価項目 |
| カメラ危険箇所 | 遮蔽、狭路、高低差 |
| 技術的復帰 | 場外、詰まり、経路なしへの対応 |
| 必要素材 | モデル、動作、音、記号 |
| 試験場面 | 正常、誤操作、敵対的操作 |

### 14.1 ステージを増やす条件

- 前のステージと異なる判断を一つ以上要求する。
- 動物数や距離だけを増やした面にしない。
- 安全な経路と熟練経路を持つ。
- 初見プレイヤーが目的を確認できる。
- 5〜10分の範囲を大きく超える停滞がない。

---

## 15. 素材制作と受け入れ条件

### 15.1 灰色の仮素材を先に使う

面白さ試作と危険検証では、単純な立体と仮動作を使う。最終モデルを先に作らない。

最終素材の制作を開始する条件は、P5の縦切り統合版が合格した後とする。

### 15.2 動物モデルの必須状態

完成動物には、少なくとも次を動きで区別できる必要がある。

- 待機。
- 通常移動。
- 主人公または音への反応。
- 警戒。
- 混乱または逃走。
- 囲い進入。
- 収容後。

危険種は、索敵、追跡、狙い、飛びかかりも区別する。

### 15.3 素材の受け入れ条件

- 高いカメラ位置でも種類を見分けられる。
- 色を消しても輪郭で区別できる。
- 姿勢から次の行動を読める。
- 目標端末の容量と描画予算に収まる。
- LODまたは簡略表示が必要な場合に対応できる。
- 出典、作者、利用条件、変更内容を記録する。
- 権利を確認できない素材を使わない。

### 15.4 音の受け入れ条件

- 誘導音と威嚇音を音量だけで区別しない。
- 危険警告が環境音へ埋もれない。
- 同時発音数を制御する。
- 音なしでも視覚情報が残る。
- ブラウザのユーザー操作後に安全に開始する。

---

## 16. 品質の優先順位

作業や性能が衝突した場合は、次の順で守る。

1. 入力が正しく反応する。
2. 動物の反応を読める。
3. カメラが必要な対象を見せる。
4. ルールが再現可能で、公平である。
5. 進行不能にならない。
6. 目標端末で安定する。
7. 結果から改善方法が分かる。
8. 音と動作の手応えがある。
9. 背景、効果、細かな装飾が美しい。
10. 動物、ステージ、設定の数が多い。

負荷が高い場合は、背景効果、影、装飾、遠景、同時発音を先に減らす。入力、予備動作、危険警告、状態表示は最後まで守る。

## 17. 制作上の主なリスク

| リスク | 兆候 | 対策 | 切り替え条件 |
|---|---|---|---|
| 中心誘導が面白くない | 動物を動かせても再挑戦しない | P2で先に確認する | 2回の大修正後も再挑戦が生まれなければ中心を再検討 |
| 間接操作が理不尽 | 原因を説明できない | 予備動作、緊張原因、固定規則 | 失敗理解率80%未満なら機能を増やさない |
| カメラが主作業になる | 常に右指で調整する | 対象保持、引き、遮蔽処理 | 手動カメラ25%超が続けば再設計 |
| 救助が複雑すぎる | 危険予告を理解しても救助できない | 救助条件と威嚇耐性を減らす | P4不合格なら救助を簡略化 |
| 得点が分からない | 合計点だけ見て改善できない | 評価、称号、助言、詳細の順 | 二回目改善率70%未満なら結果画面を修正 |
| 3D素材が制作を止める | 仮動作より見た目が先行する | P5まで仮素材 | 最終素材が中心検証を遅らせる場合は停止 |
| 1.0の範囲が膨らむ | 新動物、新環境、新設定が増える | 一つ追加するなら一つ外す | 第4動物以外は1.0後へ移す |
| 端末性能が不足 | 入力遅延、発熱、再読み込み | 段階的画質、容量予算 | iPhone 11 Proで30fps未達なら見た目を削減 |
| プレイテスター不足 | 開発者だけが理解できる | 節目ごとに少人数でも初見を入れる | P6までに初見8人未満なら公開判断を保留 |
| 元作品へ近すぎる | 比較画像で固有表現が似る | 独自の自然保護区、動物、画面 | 権利や見た目に疑義があれば公開しない |
| AI実装の一貫性が崩れる | PRごとに規則や命名が変わる | 正式文書、データ化、PR証拠 | 契約違反は後続でなく同じPRで直す |
| 解析が目的化する | 指標は多いが改善判断がない | 中心指標だけで進行判定 | 記録するが使わない指標は削除 |

## 18. Webゲームとしての公開品質

OITATEは現在GameSnacksへの提出を決めていない。ただし、GoogleのGameSnacks要件は、モバイル向けWebゲームの外部品質基準として一部を参考にする。

### 18.1 読み込み

- 1秒以内に、最初の表示または読み込み表示を出す。
- 10Mbps程度の接続で15秒以内に遊べる状態を目標にする。
- 縦切り完成版の初回ダウンロードは15MiB以下を上限目標とし、10MiB以下を目指す。
- 最初のステージに不要な素材は、開始前にすべて読み込まない。
- 読み込み失敗時に、無地画面のまま止めない。

### 18.2 対応範囲

**主基準**

- iPhone 17 Pro、Safari、横画面。

**最低確認**

- iPhone 11 Pro。
- iPad Pro 2018。
- PCの主要ブラウザ。

**方針**

- 通常Safariで横画面を強制できる前提にしない。
- 縦画面では安全に停止し、横向きを案内する。
- 画面比率が変わってもUIが切れない。
- タッチで全機能を利用できる。
- PCではマウスとキーボードで利用できる。

### 18.3 性能

- iPhone 17 Proで平均55fps以上を目標にする。
- iPhone 11 ProとiPad Pro 2018で平均30fps以上を目標にする。
- 入力反応と動物判断を、背景表現より優先する。
- 10分の連続プレイと20回の再開始で停止しない。
- 端末が熱くなり続ける場合は、画質を自動または手動で下げられるようにする。

### 18.4 権利と公開情報

- 使用OSS、素材、音、画像の出典と条件を公開前に一覧化する。
- Herdy Gerdyの名称を、公開タイトル、宣伝文、画像比較へ使用しない。
- 「同じルールの再現」ではなく、独自の動物誘導アクションパズルとして説明する。
- 対応端末、横画面、音、操作、アクセシビリティ機能を公開ページへ記載する。
- 既知問題がある場合は、隠さず公開ページへ記載する。

## 19. 公開段階

### 19.1 限定確認版

- GitHub PagesのURLを限定的に共有する。
- 検索や実験場への掲載を急がない。
- P1〜P5の確認に使う。
- 仮素材、診断表示、未完成UIを許容する。

### 19.2 公開試験版

- P6の縦切り完成版が合格した後に検討する。
- 1つの完成ステージとして公開できる。
- 「開発中」「1ステージ版」であることを明示する。
- 得点と再挑戦を一般プレイヤーへ確認する。
- 実験場へ掲載する場合は、未完成作品であることを明確にする。

### 19.3 1.0公開版

- 6ステージを含む。
- 進行保存、設定、権利、公開画像、説明を含む。
- 致命的な既知問題がない。
- ユーザーの明示承認後に公開する。

### 19.4 公開後の判断

公開直後は、新しいステージや動物より次を優先する。

1. 起動、入力、進行保存の問題。
2. 進行不能と理不尽な失敗。
3. カメラと操作。
4. 得点と結果の理解。
5. 性能と発熱。
6. 見た目と追加内容。

オンラインランキング、日替わり、追加動物は、再挑戦と得点改善が実際に確認できた後に判断する。

## 20. 公開時に必要な制作物

1. ゲーム名と短い説明。
2. 150文字以内の紹介文。
3. 512×512のアイコン。
4. 16:9の横長キービジュアル。
5. ゲーム内容が分かる3枚以上の画面画像。
6. 15〜30秒程度で中心の誘導が分かる短い映像。
7. 操作説明。
8. 対応端末と横画面の案内。
9. アクセシビリティと補助設定の説明。
10. 使用OSS、素材、権利の一覧。
11. 既知問題。
12. 更新履歴。

見た目だけの画像ではなく、主人公の位置、動物の反応、囲い、危険が一枚で分かる画像を優先する。

## 21. 1.0ステージ構成の暫定方針

具体的な配置は、縦切り完成版の結果後に決める。現在は制作量の上限として次を定める。

| 面 | 中心 | 新しい要素 |
|---|---|---|
| 練習 | 操作を安全に試す | 得点なしまたは簡易評価 |
| 1 | 接近圧力 | 臆病種、広い囲い |
| 2 | 誘導音と経路 | 追従種、浅い水 |
| 3 | 危険管理 | 危険種、威嚇音、専用囲い |
| 4 | 合図の副作用 | 臆病種と追従種の近接 |
| 5 | 群れの分裂 | 狭路、待機場所、複数入口 |
| 6 | 総合 | 3種類、複数解、総合評価 |

第4の動物が合格した場合は、既存6面の一部へ置き換える。単純に7面目を追加しない。

## 22. 実装順序への追加修正

既存の6つの大きなDraft PRは維持する。ただし、制作段階との対応を明確にする。

| 既存PR | 制作段階 | 途中の中止判定 |

## 23. 公開候補版の最終確認

### 製品

- 一文で内容を説明できる。
- 主な対象プレイヤーへ誤解のない紹介ができる。
- 3種類の違いが見た目と攻略へ表れる。
- 各面に安全な経路と熟練経路がある。
- 1.0の範囲外機能が混ざっていない。

### 初回体験

- 読み込み表示がすぐ出る。
- 設定を強制されず開始できる。
- 45〜90秒以内に最初の動物反応を理解できる。
- 説明は操作型で、再プレイ時にスキップできる。

### 操作と公平性

- 入力、カメラ、合図が同時に動く。
- 画面外、壁越し、経路なしの攻撃がない。
- 技術的な詰まりを得点や失敗にしない。
- 標準、補助あり、練習の記録が分かれる。

### 再挑戦

- 結果画面で良かった点と改善点が分かる。
- 再挑戦へ3操作以内で進める。
- 二回目に改善できる余地がある。
- 得点の詳細は必要な人だけ開ける。

### 技術

- 目標端末で性能を満たす。
- 初回ダウンロードと読み込みを測定している。
- 20回の開始、失敗、再開、クリアで状態が壊れない。
- 保存データの旧版移行または安全な初期化ができる。

### 公開

- アイコン、画像、短い映像、紹介文がある。
- 操作、横画面、対応端末、補助設定を説明している。
- 権利とライセンスを確認している。
- 既知問題を記載している。
- ユーザーが公開を承認している。

## 24. 参考にした外部指針

以下はOITATEの必須提出先ではなく、モバイルゲームとWebゲームの品質を確認する参考資料である。

### Apple

- Human Interface Guidelines: Game controls
  - https://developer.apple.com/design/human-interface-guidelines/game-controls
- Human Interface Guidelines: Designing for games
  - https://developer.apple.com/design/human-interface-guidelines/designing-for-games
- Human Interface Guidelines: Onboarding
  - https://developer.apple.com/design/human-interface-guidelines/onboarding

参考にした点：

- 左側で移動、右側でカメラを扱う。
- よく使うタッチ操作を十分な大きさにする。
- 初回から設定を要求せず、すぐ遊べる既定値を用意する。
- 説明は短く、操作型で、必要に応じてスキップできるようにする。

### Google GameSnacks

- GameSnacks requirements
  - https://developers.google.com/gamesnacks/developer/requirements

参考にした点：

- 最初の表示、遊べるまでの時間、初回容量を測る。
- タッチ、マウス、可能ならキーボードで遊べるようにする。
- 画面比率変更、停止、再開、保存、権利確認を公開品質として扱う。

GameSnacksは縦画面対応など独自要件を持つ。OITATEが同サービスへ提出することは、本書では決定しない。

### Microsoft

- Xbox Accessibility Guidelines
  - https://learn.microsoft.com/en-us/gaming/accessibility/guidelines

参考にした点：

- 設計初期からアクセシビリティを確認する。
- UIの目的と操作結果を理解できるようにする。
- 難しさを一つの速度だけで決めず、補助方法を用意する。
- 機能を実際の対象プレイヤーと早い段階で試す。

### GameAnalytics

- Metrics all game developers should know
  - https://www.gameanalytics.com/blog/metrics-all-game-developers-should-know

参考にした点：

- 継続率、プレイ時間、1回の長さだけでなく、どこで離脱し、再挑戦するかを見る。

外部の平均値は、OITATEの合否を直接決める基準にはしない。

## 25. 実装開始条件

次を満たすまで、ゲームコードの実装を開始しない。

1. 本書のDraft PRが確認される。
2. 既存4文書と本書の役割がREADMEへ反映される。
3. ユーザーが本書を承認する。
4. ユーザーが明示的に「実装開始」と指示する。
5. 最初の作業をP1の操作試作として扱う。
6. P1が不合格の場合、動物や得点へ進まない。

本書のマージは、実装開始の指示とは扱わない。
