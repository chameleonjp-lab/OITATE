## 1. 計画の要約

OITATEは、主人公が複数種類の動物を観察し、それぞれに適した方法で誘導し、指定された囲いへ収容する3Dアクションパズルゲームとする。

中心となる面白さは、単に動物を後ろから追うことではない。動物ごとに、主人公への反応、音への反応、群れ方、危険な相手、通れる地形を変える。プレイヤーは状況を読み、危険な動物を先に隔離するなど、作業の順序を考えて行動する。

Herdy Gerdyから参考にするのは、次の抽象的な仕組みに限る。

1. 主人公の位置や行動によって動物を間接的に動かす。
2. 動物の種類ごとに誘導方法と性質が異なる。
3. 捕食や地形の相性によって、誘導する順序が変わる。
4. 種類ごとに適切な囲いへ収容すると目的を達成する。

固有名詞、キャラクター、動物デザイン、ステージ形状、物語、台詞、音、画像、画面構成は使用しない。既存作品を見た目まで再現するのではなく、ルール上の役割を独自の表現へ置き換える。

本計画では、まず1ステージでゲームの中心が成立する最小版を完成させる。その後、動物、地形、ステージ、評価方法を増やす。

## 2. 固定する開発方針

本計画で採用する方針は次のとおりとする。

| 項目 | 採用方針 |
|---|---|
| 画面 | 横画面の3D、斜め後方から見下ろす三人称視点 |
| 基準端末 | iPhone 17 Proを主基準とし、iPhone 11 ProとiPad Pro 2018も確認する |
| 開発言語 | TypeScript |
| 3D表示 | Three.js |
| 道順探索 | Navcatを第一候補とし、適合試験に失敗した場合はrecast-navigation-jsへ切り替える |
| 地形判定 | three-mesh-bvh |
| 動物の判断 | OITATE専用の小さな判断処理を作る。Yukaは設計参考に留める |
| 物理演算 | 最小版では一般的な物理エンジンを使わない |
| 画面部品 | HTMLとCSS。Reactは導入しない |
| 保存 | 最小版では端末内保存のみ |
| サーバー | 最小版では使用しない |
| 公開 | GitHub Actionsで検査と作成を行い、GitHub Pagesへ公開する |
| 実装管理 | 1作業につき1つのDraft PR。mainへ直接実装しない |

物理演算を最初から使わない理由は、動物同士の押し合い、柵のすり抜け、入口での積み重なりなど、パズルに不要な不安定さを増やさないためである。主人公と動物は、歩ける場所の上を制御された速度で移動させる。

## 3. 類似OSS調査の結論

## 4. ゲームの設計目標

### 4.1 プレイヤーに考えてもらうこと

プレイヤーには、次の流れを繰り返してもらう。

1. 動物の配置、囲い、危険、地形を観察する。
2. どの動物を先に動かすか決める。
3. 接近、誘導音、威嚇音を使い分ける。
4. 動物の反応を見て、自分の位置と経路を調整する。
5. 収容結果を確認し、次の群れへ移る。

操作の速さだけでなく、予測と順序で上達できるゲームにする。

### 4.2 失敗の考え方

失敗は、プレイヤーが原因を理解できる形にする。

- 危険種を放置したため、保護対象が襲われた。
- 間違った誘導音を使い、別の群れを危険区域へ動かした。
- 動物の通れない地形へ追い込んだ。
- 囲いの入口を主人公自身が塞いだ。

動物の気まぐれだけで失敗させない。重要な判断には、再現性のある規則を使う。

### 4.3 読みやすさ

動物が何に反応したかを、次の複数の方法で示す。

- 頭や体の向き
- 移動開始前の短い予備動作
- 小さな状態アイコン
- 種類ごとに異なる鳴き声や反応音
- 囲いの形、記号、旗

色だけでは区別しない。消音状態でも遊べるようにする。

### 4.4 やり直しやすさ

最小版では、失敗後すぐに同じ配置から再開できるようにする。長い説明画面や読み込みを挟まない。

動物が角や柵で止まった場合は、自動で離脱方向を探す。プレイヤーが正しい操作をしていても進行不能になる状態を残さない。

## 5. 最小版のゲーム内容

最小版は、機能を確認するだけの技術試作ではなく、順序パズルが成立する1ステージとする。

### 5.1 登場要素

| 要素 | 数 | 役割 |
|---|---:|---|
| 主人公 | 1 | 移動、接近による圧力、誘導音、威嚇音を使う |
| 臆病種 | 6 | 主人公から逃げる。仲間へ寄り、単独になることを嫌う |
| 追従種 | 4 | 接近だけでは動きにくく、誘導音を聞くと主人公についてくる |
| 危険種 | 1 | 保護対象を追う。威嚇音を聞くと主人公を優先して追う |
| 種類別の囲い | 3 | 対応する種類だけを収容する |
| 地形問題 | 1組 | 浅い水場または狭い橋。種類ごとに通行条件を変える |

合計11体の動物を扱う。

### 5.2 誘導方法

#### 接近による圧力

主人公が一定距離まで近づくと、臆病種が主人公と反対方向へ移動する。走ると圧力が強くなり、歩くと細かく調整できる。

#### 誘導音

追従種が主人公の方を確認し、一定時間ついてくる。壁越しには反応させない。距離が離れすぎた場合は、現在地で待つか仲間へ戻る。

#### 威嚇音

臆病種には短い散開を起こす。危険種には主人公を優先して追う行動を起こす。連続使用には短い待ち時間を設ける。

### 5.3 順序パズル

基本解は次の流れを想定する。

1. 危険種を威嚇音で主人公へ向ける。
2. 保護対象から引き離し、危険種専用の囲いへ誘導する。
3. 誘導音で追従種を安全な経路へ運ぶ。
4. 主人公の立ち位置を使い、臆病種をまとめて囲いへ追い込む。

ただし、操作を一手間違えただけで即座に詰む構造にはしない。危険種を再び引きつける、散った群れを集め直すなど、回復手段を残す。

### 5.4 クリアと失敗

**クリア条件**

- 3種類すべてが、対応する囲いへ必要数収容される。
- 危険種が隔離され、保護対象が残っている。

**失敗条件**

- 危険種が保護対象へ有効な攻撃を成立させる。
- 保護対象が復帰不能な場外へ出る。

最小版では、動物の残数を減らしたまま続ける方式ではなく、失敗理由を表示して即時にやり直す方式を採る。原因を理解しやすくするためである。

### 5.5 最小版に入れない内容

- 複数ステージ
- オンラインランキング
- ユーザー登録
- 物語と会話イベント
- 収集物
- 本格的なレベル編集機能
- 複雑な剛体物理
- 装備、成長、課金
- 制限時間による強制失敗

制限時間は、基本ルールの安定後に評価項目として検討する。

## 6. 操作とカメラ

### 6.1 iPhone操作

横画面を標準とする。

- 左側：仮想スティックで主人公を移動する。
- 右側の空き領域：ドラッグでカメラを左右へ回す。
- 右下：誘導音ボタン。
- 右下：威嚇音ボタン。
- 主人公の接近圧力：自動で発生する。
- 一時停止：画面上部のボタン。

操作部品はiPhoneの安全領域を避ける。画面端からのスワイプやブラウザ操作と競合しない配置にする。

### 6.2 補助操作

PCでは、移動をWASDまたは矢印キー、カメラをマウス、誘導音と威嚇音をキーで操作できるようにする。PC操作は補助対応であり、画面設計はiPhoneを優先する。

### 6.3 カメラ

- 主人公の斜め後方かつ高めから追従する。
- 主人公が進む方向へ緩やかに戻る。
- 手動回転中は自動補正を弱める。
- 地形や木が主人公を隠す場合は、カメラを前へ寄せるか、遮る物を一時的に透過する。
- カメラを壁や地面へ入れない。
- 急な向き変更で画面を大きく揺らさない。

## 7. システム構成

### 7.1 全体の責務

| 層 | 責務 |
|---|---|
| アプリ管理 | 起動、読み込み、画面遷移、一時停止、エラー表示 |
| ゲーム進行 | 開始、クリア、失敗、やり直し、経過時間、収容数 |
| 世界 | 地形、柵、囲い、水場、開始位置、カメラ対象 |
| 主人公 | 入力、移動、音の発生、接近圧力 |
| 動物判断 | 視認、音の受信、危険判定、優先行動の選択 |
| 群れ移動 | 仲間へ寄る、近づきすぎない、向きを合わせる |
| 道順 | 歩ける範囲、地形ごとの通行条件、経路の再計算 |
| 表示 | 3Dモデル、アニメーション、効果、音、状態アイコン |
| 画面部品 | 仮想スティック、行動ボタン、目的、結果、設定 |
| データ | 動物設定、ステージ設定、囲い設定、調整数値 |

動物の判断と3Dモデルを分ける。見た目を変更しても、行動規則を作り直さずに済む構成にする。

### 7.2 動物の判断手順

各動物は、次の順番で行動を決める。

1. 周囲の主人公、仲間、敵、囲い、地形、音を調べる。
2. 現在もっとも重要な出来事を選ぶ。
3. 行動状態を決める。
4. 進みたい方向と目的地を決める。
5. 歩ける場所へ進行方向を収める。
6. 実際の位置と向きを更新する。
7. 表示側へ、移動、待機、驚き、追跡などの状態を伝える。

行動の優先順位は次のとおりとする。

**収容済み ＞ 即時の地形危険 ＞ 捕食・逃走 ＞ 主人公の誘導 ＞ 群れの維持 ＞ 通常行動**

これにより、囲いへ入った動物が再び外へ出る、捕食者が目の前にいるのに音へ従う、といった矛盾を防ぐ。

### 7.3 行動状態

共通状態は次のとおりとする。

- 待機
- 通常移動
- 群れへ復帰
- 主人公から逃走
- 主人公へ追従
- 対象を追跡
- 危険から逃走
- 経路を探し直す
- 囲いへ進入
- 収容済み
- 一時停止

種類固有の状態は、共通状態を壊さず追加できるようにする。

### 7.4 更新頻度

3D表示は端末が許す範囲で滑らかに描画する。動物の重い判断は毎画面更新で行わず、原則として1秒に20回の固定間隔で更新する。

見た目の位置は前後の結果を滑らかにつなぐ。これにより、判断処理の負荷を抑えながら、動きの粗さを見せない。

### 7.5 再現性

ステージ開始時に乱数の種を決める。開発中は同じ種を指定すると同じ初期行動を再現できるようにする。

不具合報告には、ステージ番号、乱数の種、経過時間、動物状態を含める。偶然にしか起きない不具合を追跡しやすくする。

### 7.6 群れの計算

群れの動きは、次の力を組み合わせる。

- 仲間へ近づく。
- 仲間へ近づきすぎない。
- 周囲の仲間とおおよその向きを合わせる。
- 主人公、敵、壁から離れる。
- 音や目的地へ向かう。

すべての動物同士を毎回比較すると、数が増えたときに重くなる。空間を区画に分け、近い区画の動物だけを調べる。

### 7.7 道順

Navcatで、地形上の歩ける面を管理する。ステージ公開時には歩行データをあらかじめ作成し、プレイ開始時は読み込むだけにする。

地形には種類を付ける。

- 通常地面
- 浅い水
- 狭い道
- 危険区域
- 囲い内部
- 進入禁止

動物の種類ごとに、通行可能か、移動にどれだけ負担があるかを変える。

Navcatは比較的新しい0.x系であるため、最初の工程で適合試験を行う。次の条件を満たさない場合は、recast-navigation-jsへ切り替える。

- iPhone Safariで初期化と読み込みが安定する。
- 11体が同時に経路を更新しても操作が止まらない。
- 囲いの狭い入口で経路が壊れない。
- 地形ごとの通行条件を種類別に設定できる。
- 10分間の連続動作でメモリ使用量が増え続けない。

### 7.8 地形との接触

three-mesh-bvhを、次の用途に限定して使う。

- 主人公の足元の高さを求める。
- 崖や壁への接触を調べる。
- カメラと地形の間を調べる。
- 音や視認が壁を越えていないか確認する。

動かない地形だけに高速化用データを作る。毎画面、地形全体を作り直さない。

## 8. 技術選定

| 分野 | 採用 | 理由 |
|---|---|---|
| 言語 | TypeScript | 動物設定と状態の不一致を早期に見つけやすい |
| 開発と作成 | Vite | 構成が小さく、Three.jsの標準的なモジュール構成と合わせやすい |
| 3D | Three.js | 必要な機能だけを組み合わせやすく、特殊な動物規則を独立して作れる |
| 道順 | Navcat | 純JavaScript、型定義、保存可能な歩行データ、Three.js連携がある |
| 道順の予備 | recast-navigation-js | Navcatで不足した場合に、実績のある道順と群衆機能を使える |
| 地形判定 | three-mesh-bvh | Three.jsの地形への接触とカメラ判定を高速化できる |
| 単体試験 | Vitest | TypeScriptの計算処理をブラウザ表示から切り離して確認できる |
| ブラウザ試験 | Playwright | 開始、操作、失敗、再開、クリアの一連の流れを確認できる |
| 継続検査 | GitHub Actions | PCを持たない運用でも、クラウド上で毎回同じ検査ができる |
| 公開 | GitHub Pages | 静的なブラウザゲームとして公開できる |

### 8.1 採用しない候補

**Babylon.js**は総合機能が豊富だが、今回の中心である動物判断まで一つのエンジンへ寄せる必要はない。OITATEでは、表示、判断、道順を分離しやすいThree.jsを選ぶ。

**PlayCanvas**はブラウザ編集が利点だが、外部エディター上の状態とGitHub上の状態を二重管理する危険がある。最小版はJSONのステージ設定と小さな調整画面で管理する。

**Yuka**は動物判断の機能が近いが、OITATE固有の優先順位がゲーム性そのものである。最小版では専用処理を作り、必要性が明確になった場合だけ依存を再検討する。

**Rapier**などの物理エンジンは、押せる物、落下物、動く橋などを追加する段階まで保留する。

### 8.2 バージョン管理

- 依存関係は厳密な版で固定する。
- ロックファイルを保存する。
- 本番公開前に、利用ライセンス一覧を出す。
- 機能開発中に自動で大きな版を更新しない。
- 更新は専用PRで行い、iPhone実機確認後に取り込む。

## 9. 予定するリポジトリ構成

実装時は、概ね次の責務で分ける。ここでは構成だけを定め、まだファイルは作らない。

| 場所 | 役割 |
|---|---|
| `src/app` | 起動、画面遷移、エラー、一時停止 |
| `src/game` | ゲーム進行、クリア、失敗、やり直し |
| `src/world` | 地形、囲い、危険区域、ステージ読み込み |
| `src/player` | 主人公、入力、カメラ対象、誘導行動 |
| `src/animals` | 共通動物処理、種類別設定、行動状態 |
| `src/simulation` | 固定間隔更新、乱数、空間区画、時間管理 |
| `src/navigation` | Navcatまたは予備ライブラリとの接続 |
| `src/rendering` | Three.js、モデル、照明、アニメーション、効果 |
| `src/ui` | タッチ操作、目的表示、設定、結果 |
| `src/data` | ステージ、動物、囲い、調整数値 |
| `src/debug` | 状態表示、経路表示、乱数の種、負荷計測 |
| `tests` | 行動規則、統合試験、ブラウザ試験 |
| `public/assets` | 許諾確認済みの3Dモデル、音、画像 |
| `docs` | 仕様、計画、ライセンス、調整記録 |

ゲーム規則からThree.jsやNavcatを直接呼び出さない。接続部分を薄い層へ隔離し、ライブラリを変更しても動物規則への影響を抑える。

## 11. 試験計画

### 11.1 動物規則の自動試験

次の内容を、3D表示から切り離して試験する。

- 主人公が反応範囲外なら、臆病種が逃げない。
- 主人公が反応範囲内なら、臆病種が反対方向を選ぶ。
- 追従種が誘導音へ反応する。
- 壁がある場合、音または視認が遮られる。
- 危険種が最も条件に合う対象を選ぶ。
- 威嚇音がある間、危険種が主人公を優先する。
- 収容済み状態が他の行動より優先される。
- 間違った囲いでは収容数が増えない。
- 捕食判定が壁越しに成立しない。
- 経路がなくなった場合、再探索状態へ移る。

### 11.2 場面単位の統合試験

- 危険種を隔離してから、残り2種類を収容できる。
- 先に保護対象を動かすと危険が生じる。
- 誘導音と威嚇音を続けて使った場合、優先順位が崩れない。
- 囲いの入口に複数体が集まっても進行不能にならない。
- 一時停止中に判断、経過時間、捕食が進まない。
- やり直し後に前回の状態が残らない。
- 20回連続で開始と終了を繰り返しても状態が壊れない。

### 11.3 ブラウザ試験

Playwrightで、少なくとも次を自動確認する。

- 起動できる。
- 開始画面からゲームへ進める。
- 入力に応じて主人公が移動する。
- 行動ボタンが反応する。
- 失敗画面から再開できる。
- クリア画面へ到達できる開発用経路がある。
- 画面幅を変えても操作部品が画面外へ出ない。
- ブラウザのコンソールに未処理エラーが出ない。

### 11.4 実機確認

| 端末 | 主な確認 |
|---|---|
| iPhone 17 Pro | 基準性能、操作感、60フレーム毎秒の目標、発熱 |
| iPhone 11 Pro | 低い処理性能での30フレーム毎秒維持、メモリ、読み込み |
| iPad Pro 2018 | 大画面配置、カメラ、操作部品の中央配置、画面比率 |
| PCブラウザ | キーボード、マウス、画面拡大時の配置 |

## 12. 性能目標

性能値は、最小版の完成判定に使う目標値とする。測定結果に応じて、見た目より操作の安定を優先する。

| 指標 | 目標 |
|---|---|
| iPhone 17 Pro | 通常プレイの平均55フレーム毎秒以上。2秒を超えて45未満へ落ち続けない |
| iPhone 11 Pro | 通常プレイの平均30フレーム毎秒以上。2秒を超えて24未満へ落ち続けない |
| iPad Pro 2018 | 通常プレイの平均30フレーム毎秒以上 |
| 動物数 | 11体で安定。開発試験では20体も確認する |
| 初回読み込み | 圧縮後20MB以内を目標とする |
| 表示三角形 | 通常画面で15万以下を目安とする |
| 描画回数 | 通常画面で120以下を目安とする |
| 連続動作 | 10分間、停止、再読み込み、入力不能が起きない |
| 再開 | 失敗から同じ場面の操作可能状態まで2秒以内を目標とする |

負荷が高い場合は、次の順で削減する。

1. 影の解像度と対象数。
2. 遠景の細かさ。
3. 3Dモデルの面数。
4. 動物判断の更新頻度。
5. 画面効果。

動物の反応精度と入力の遅延は、最後まで優先する。

## 13. 最小版の完成条件

### 13.1 ゲームとしての完成

- 3種類の動物が、見た目だけでなく規則上も明確に異なる。
- 危険種を先に隔離する順序問題が成立する。
- 接近、誘導音、威嚇音の3方法を使い分ける必要がある。
- 地形の違いが、少なくとも1種類の動物の経路選択へ影響する。
- 正しい手順で必ずクリアできる。
- 失敗理由が表示され、プレイヤーが次の試行で改善できる。
- ランダムな挙動だけで詰まない。

### 13.2 操作と表示の完成

- iPhone横画面で片手ずつ役割を分けて操作できる。
- カメラが地形へ入り込まず、主人公を見失いにくい。
- 重要な状態を色以外でも見分けられる。
- 消音状態でもクリアに必要な情報が分かる。
- ピンチ拡大、長押し選択、不要な横スクロールがゲーム操作を妨げない。

### 13.3 技術的な完成

- 型確認、単体試験、ブラウザ試験、公開用作成が成功する。
- 未処理のエラーがブラウザへ出ない。
- 同じ乱数の種で重要な不具合を再現できる。
- 動物が3秒以上同じ障害物へ押し続けた場合、離脱または再探索する。
- 20回連続で開始、失敗、再開、クリアを行っても状態が壊れない。
- 性能目標を満たすか、満たせない項目と理由を文書化する。

### 13.4 運用上の完成

- 使用したOSS、素材、生成物の出典と利用条件を記録する。
- ライセンス未指定の類似ゲームからコードと素材を取り込まない。
- 設定値をソース内へ散らさず、動物またはステージのデータとして管理する。
- 開発者表示は通常プレイヤーから見えない。
- 公開版へ秘密情報、管理用キー、個人情報を含めない。

## 14. 主なリスクと対策

| リスク | 起きる問題 | 対策 | 方針変更の基準 |
|---|---|---|---|
| 群れの動きが不安定 | 入口で詰まる、急に散る | 優先順位を固定し、群れの力へ上限を設ける。再現用の乱数を保存する | 正しい操作でも5回中1回以上詰まる場合、規則を簡略化する |
| NavcatがiPhoneで不安定 | 初期化停止、経路失敗 | PR 1で先に適合試験する | 完了条件を満たさない場合、recast-navigation-jsへ切り替える |
| 3D表示が重い | 入力遅延、発熱 | 影、面数、描画回数、効果を予算化する | iPhone 11 Proで30を維持できない場合、見た目を軽くする |
| カメラが見づらい | 主人公や群れを見失う | 高めの視点、壁判定、透過、緩やかな自動補正 | 手動回転が頻繁に必要なら、視点とステージ形状を見直す |
| タッチ操作が競合 | カメラと行動ボタンの誤操作 | 入力領域を明確に分け、複数指を別々に追跡する | 誤操作が繰り返す場合、固定ボタン配置と感度を調整する |
| 捕食が理不尽 | 壁越し攻撃、反応不能 | 視認、経路、攻撃予備動作、接触条件を分ける | 原因を画面で説明できない失敗は公開しない |
| 範囲が増えすぎる | 最小版が終わらない | 1ステージ、3種類、11体を固定する | 新要素は最小版完成後の一覧へ移す |
| 素材の権利が不明 | 公開停止の危険 | 自作、明確な許諾、利用記録を必須にする | 許諾を確認できない素材は使用しない |
| PCなしの開発 | ローカル作成や試験が難しい | GitHub ActionsとGitHub Pagesで作成と公開を自動化する | 手作業が必要な工程はブラウザ上の小さな調整機能へ置き換える |

## 15. 開発中だけ使う確認機能

群れの不具合は、見た目だけでは原因を追いにくい。通常プレイヤーには見せず、開発中だけ次を表示できるようにする。

- 動物ごとの現在状態。
- 現在の目的地。
- 選んだ経路。
- 主人公、音、敵への反応範囲。
- 囲いの判定範囲。
- 乱数の種。
- 1秒ごとの判断回数。
- 画面更新速度と動物判断に使った時間。
- 詰まりからの復帰回数。

この表示は、URLの開発用指定または開発版だけで有効にする。公開版の通常画面には表示しない。

## 16. 最小版後の拡張候補

最小版の完成後に、次の順で検討する。

1. 動物を6種類へ増やす。
2. ステージを6面へ増やす。
